把 SDD 装进仓库

开发者只说一次需求，Agent 按仓库里的 next.action 自动调研、写工件、推进阶段。你只在两个地方出现：确认 Spec，确认交付。

不是再写一份流程文档

把流程放进状态机，让每个 Agent、每个仓库走同一条路径。规则在 Git 里，不在某个人的 IDE 配置里。

01

任何 Agent，同一套规则

规则、状态和工件都在仓库里。Claude Code、Cursor、Kiro 或自研 Agent，只要能执行 shell，就调用同一个 CLI。

python -m sdd resume --json
02

开发者零初始化

平台团队 bootstrap 一次，开发者 clone 后直接开始。不注册 workflow，不装个人插件，不改业务代码结构。

git clone && python -m sdd resume
03

流程能被强制

Git Hook 与 CI 校验工件和 Gate。Agent 不能代替人执行 approve 或 merge，跳过步骤会在提交时暴露。

python -m sdd check --all --stage ci

一次需求，两个人工检查点

其余步骤由 Agent 按 next.action 自动推进。每次提交都由 CLI 重新校验，失败就按错误列表修复。

  1. 01

    恢复或开始

    resume 判断会话绑定哪个 Spec；没有就 start-work。调研事实写进 context.md，未决问题写进 unknowns.md。

  2. G1

    人确认 Spec

    人执行 approve --human。Agent 停在这里，不代替人做需求判断。

  3. 02

    设计与拆任务

    设计写清模块边界、接口契约和回滚；任务表保证每条 AC 都有覆盖、有测试命令、有真实依赖顺序。

  4. 03

    逐 Task 实现

    失败测试先行。submit-task 必须带上执行过的命令、目录和结果，状态机才认这个任务完成。

  5. 04

    验证并准备 PR

    report 生成 PR 正文；CI 执行 verify-core、verify-agent 和全量检查，证据留在 Git 里。

  6. G2

    人确认交付

    人执行 merge --human。状态机进入 MERGED；随后 Agent 才创建 PR，由管理员合并。

一个状态机，三层薄边界

Agent 只看见协议，协议只调用 CLI，CLI 只调用状态机。任何一层都不复制另一层的规则。

AgentAGENTS.mdpython -m sddsdd.pyGit
协议层

AGENTS.md 是唯一入口

托管块告诉 Agent 先 resume，再按返回的动作执行。0.8 起支持 l2-standard、l2-hotfix、l2-strict 命名预设，创建 Spec 时固定。

状态机

规则只写一次

sdd/scripts/sdd.py 负责阶段、工件校验、Gate 和事件日志。不要在提示词、Hook 或 MCP 里复制这些规则。

适配层

MCP 只是包装

MCP 把同一套 CLI 能力变成结构化工具。没有 MCP，AGENTS.md + CLI + Hook + CI 仍然能跑完整流程。

Agent 看到的下一步 实时返回 
{
  "action": "implement_task",
  "task": "T-001",
  "artifact": "tasks.md",
  "submit_with": "sdd submit-task",
  "human_checkpoint": {
    "required": false
  }
}

阶段、下一步和是否停下都由 CLI 决定。Agent 不需要猜，也不应该问开发者“现在是什么阶段”。

三条命令，从 clone 到可验证

平台团队做一次接入；开发者每次只恢复会话；合并前跑同一组校验。

平台团队 · 每仓库一次

接入核心与托管块

powershell
python bootstrap.py --target "D:\repos\order-api" `
  --project order-api `
  --test-command "python -m pytest -q" `
  --ci gitlab

复制 sdd/ 核心、合并 AGENTS.md 托管块、安装 Hook 与 CI 模板。

开发者 · 每次会话

恢复当前工作

powershell
git clone <repo>
cd <repo>
python -m sdd resume --json

不需要初始化。Agent 读到 next.action 后直接继续。

合并前 · 每次

跑同一组校验

powershell
python -m unittest discover -s tests -v
python -m sdd verify-core
python -m sdd verify-agent
python -m sdd check --all --stage ci

CI 执行同样的命令。核心被改、托管块漂移或工件缺失都会失败。

命令不多，边界很清楚

Agent 用前四条，人只用两条带 --human 的命令。其余是只读查询与校验。

命令执行者作用
sdd resume --jsonAgent恢复当前 Spec，返回唯一的下一步
sdd start-workAgent把工作项绑定到新的 Spec
sdd start-work --workflow l2-strict人为高风险变更选择命名工作流
sdd submitAgent提交阶段工件并接受校验
sdd submit-taskAgent完成一个任务并记录测试证据
sdd reportAgent生成 PR 正文与 Gate 摘要
sdd approve --human人确认 Spec，DRAFT 进入 SPEC_READY
sdd merge --human人确认交付，PR_READY 进入 MERGED；之后才创建 PR
sdd check --allCI校验全部工件、Gate 与 Git 状态

适合的团队，不适合的场景

它是一套仓库内工作流，不是通用的项目管理 SaaS。边界越清楚，接入越快。

适合

  • 多个业务仓库，需要统一 L2 流程与审计证据
  • 团队混用 Claude Code、Cursor、Kiro 或自研 Agent
  • 已有 AGENTS.md，希望增量接入而不是推倒重来
  • Git 与 CI 已是默认基础设施

不适合

  • 单人一次性脚本，没有 Spec、Gate 或合并流程
  • 没有 Git 或 CI，无法留下可校验证据
  • 需要集中式 Web 审批台；当前只有 CLI 与 MCP
  • 希望工具替代需求判断或代码评审

常见问题

接入前最常被问到的六个问题。

没有 MCP 能跑吗？

能。完整路径是 AGENTS.md → python -m sdd → Git Hook / CI。MCP 只是给 Agent 的结构化适配层。

会覆盖我已有的 AGENTS.md 吗？

不会。bootstrap 只把 SDD:MANAGED 托管块合并进去，原有项目规则保留；升级时也只替换托管块。

业务仓库要修改 sdd/ 核心吗？

不要。核心由平台团队维护，业务团队只维护 sdd/config.json、sdd/context/ 和 docs/specs/。

为什么只有两个人工检查点？

需求确认和最终合并是仅有的高价值人工决策。其余步骤由测试、工件校验和 Gate 报告提供证据，不靠人反复点确认。

支持 GitLab 吗？

支持。仓库同时提供 GitHub Actions 与 GitLab CI 模板，校验命令一致。

核心怎么升级？

平台仓库打 tag，同步 bot 向业务仓库开 PR，只更新 sdd/ 核心；CI 跑 verify-core、verify-agent 和全量检查后由 CODEOWNERS 合并。
