证据在聊天里。

所以，我们把流程做成仓库里的状态机。

02 / 方法：一个状态机，一条薄链路 →

02 / 方法

一个状态机，一条薄链路。

Agent 只看见协议，协议只调用 CLI，CLI 只调用状态机。

Agent 任意 harness Claude Code · Cursor · Kiro
AGENTS.md 托管协议 只合并 SDD:MANAGED 块
python -m sdd 唯一入口 会话、校验、Gate
Git / CI 证据与强制 工件、报告、审计链

MCP 只是可选适配。没有它，CLI + Hook + CI 仍然能跑完整流程。

03 / 机制：一次需求，只停两次 →

03 / 机制

一次需求，只停两次。

其余阶段由 next.action 自动推进；失败就按 errors 修复。

  1. DRAFT写 Spec
  2. SPEC_READY人确认 Spec
  3. DESIGN_READY设计
  4. TASKS_READY任务
  5. IMPLEMENTING实现
  6. VERIFYING验证
  7. PR_READY待交付
  8. MERGED人确认交付

merge 是交付确认，不执行 Git 合并；之后 Agent 创建 PR，由管理员合并。

04 / 结果：人只做两个决定 →

04 / 结果

人只做两个决定。

Agent 负责循环，人保留判断。其余都写成可校验的证据。

Agent 循环

resume → submit → submit-task → report

人的边界

sdd approve --human · sdd merge --human

PR 审核与合并仍按仓库原有规则执行。reapprove、rewind、unblock、waive 是人工例外动作。

05 / 开始：接入一次，clone 即用 →

05 / 开始

接入一次，之后 clone 即用。

平台团队做一次 bootstrap；开发者不初始化、不装插件、不记阶段。

平台团队 · 每仓库一次

接入

powershell
python bootstrap.py
开发者 · 每次会话

恢复

powershell
python -m sdd resume --json
合并前 · 每次

校验

powershell
python -m sdd verify-core
python -m sdd verify-agent
python -m sdd check --all --stage ci

完整命令与接入参数见 sdd/README.md。

07 / 边界：适合谁，不适合谁 →

07 / 边界

适合多仓库、异构 Agent 团队。

适合

  • 多个业务仓库，需要统一 L2 流程与证据
  • 团队混用 Claude Code、Cursor、Kiro 或自研 Agent
  • 已有 AGENTS.md，Git 与 CI 是默认设施

不适合

  • 单人一次性脚本
  • 没有 Git 或 CI
  • 需要集中式 Web 审批台，或希望工具替代判断
08 / 问答：三个常见问题 →

08 / 问答

三个常见问题。

没有 MCP 能跑吗？

能。AGENTS.md → python -m sdd → Git Hook / CI 是完整路径；MCP 只是可选适配。

会覆盖已有 AGENTS.md 吗？

不会。bootstrap 只替换 SDD:MANAGED 块，原有规则保留。

为什么只有两个人工检查点？

Spec 确认和交付确认是仅有的高价值判断；其余由测试、Gate 和证据保证。
