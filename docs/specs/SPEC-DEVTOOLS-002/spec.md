## 2. 范围声明

- In-Scope：
  1. 建立官方 P0–P5、G0–G5 与 `sdd-kit` 状态、工件、检查、证据之间的逐项符合性映射，并记录“已自动、已人工、部分实现、未实现”四种状态。
  2. 打通 `工作项 → FEAT → Spec → FR/AC → Task → 测试 → Gate 证据` 的机器可读追溯链。
  3. 将 G0 需求侧准入与 G1 Spec 准入拆成独立检查组，在 Gate 报告中保留稳定检查 ID 和两组完整结果。
  4. 为 `resume --json` 增加按当前状态生成的最小只读 `context_bundle`。
  5. 为代码类变更建立可复验的 G4/G5 证据：命令、目录、退出码、关键输出、测试定位和独立审查结论。
  6. 将工作流配置升级为声明式 Profile v2，提供字段校验、检查项组合、人工检查点、风险规则、上下文规则和版本快照。
  7. 建立 Gate 检查项注册表，支持 `pass/warn/block`、强制项、建议项、人工豁免、到期重校验和按检查 ID 统计。
  8. 建立“通用 Review 契约 + Python、Java/Spring、前端 overlay”的按需加载审查能力。
  9. 建立最小知识索引，支持 `SRC/FACT/BR/CONFLICT/GAP`，并让 Spec/Design 只引用不复制。
  10. 建立 `BAR → Fix Pattern → CHK → 回归测试` 闭环，并把适用 Pattern 带入上下文包和指标。
  11. 同步 CLI、JSON schema、测试、README、Agent 协议、版本号和 manifest，保持旧 Spec 快照稳定。
- Out-of-Scope：
  1. 不实现任意 DAG 编辑器、可视化编排器或脚本化状态机。
  2. 不引入服务端控制面、数据库、常驻守护进程或集中式 Web 审批台。
  3. 不建设全量 Ontology、企业级 SSOT 平台或自动业务决策系统。
  4. 不原样复制专业公司 v7 的工具包、模板集和技能库。
  5. 不增加计划内人工检查点；`l2-standard` 仍只有 Spec 确认与 PR 合并两个计划内检查点。
  6. 不允许 Agent 自动执行 `approve`、`merge`、`unblock`、`rewind` 或 Gate 豁免。
  7. 不改变 `sdd/scripts/sdd.py` 作为唯一状态机的架构边界。
  8. 不为低风险、纯文档变更强制增加无业务价值的测试或审批仪式。

## 3. 业务上下文

### 3.1 干系人与角色

| 角色 | 诉求 | 使用场景 | 责任边界 |
|---|---|---|---|
| 平台维护者 | 用最小运行依赖维持唯一状态机和升级兼容 | 维护核心、发布版本、接入业务仓库 | 维护状态机、Profile 解释器、检查注册表和发布物 |
| 业务开发者 | clone 后直接恢复工作，不被阶段问题打断 | 日常开发、恢复会话、提交验证 | 提供工作项、确认 Spec、合并 PR、处理例外决策 |
| 执行 Agent | 每轮只拿到一个动作和最小必要上下文 | 自动循环、实现任务、提交证据 | 不改状态文件，不代替人审批，不越出允许范围 |
| 质量与合规人员 | 能按官方 Gate、检查 ID 和证据回放每一步 | 审计、抽查、复盘、质量度量 | 确认业务规则、审批例外、判定安全红线 |
| 工作流设计者 | 只写声明式 Profile 即可定义流程变体 | 新增重构、热修、严格流程 | 保证 Profile 合法、版本化、可快照 |
| 独立评审者 | 按技术栈获得结构化 finding 输入 | 中高风险变更评审 | 独立给出证据、严重度和阻断结论 |

### 3.2 业务流程

1. 人提供工作项；系统在 PRD 索引中建立唯一 FEAT，并与 Spec 元数据双向对应。
2. G0 检查需求来源、FEAT 唯一性、澄清状态和工作项一致性；G1 检查 Spec 结构、FR/AC 完整性和可执行性。
3. 人确认 Spec 后，系统生成设计、任务和当前任务的 `context_bundle`。
4. Agent 只依据上下文包定位任务、关联 FR/AC、设计章节、契约、约束、允许改动范围和适用 Fix Pattern。
5. 实现后通过统一验证命令记录可复验证据；G4 检查实现、测试定位和审查 finding，G5 检查运行证据与 AC 覆盖。
6. 所有 Gate 以稳定检查 ID 输出 `pass/warn/block`；人工豁免只由人执行并带范围、原因、审批人、到期时间和证据。
7. PR 合并后，事件链保留 actor、时间、状态迁移、产物哈希、证据和下一步，供审计与指标回流。
8. 真实缺陷经 BAR 形成 Fix Pattern 和可执行检查，下一次同类任务通过上下文包自动获得提示。

### 3.3 业务规则

- BR-001：唯一状态机仍是 `sdd/scripts/sdd.py`；Profile、CLI、MCP、Review 和 CI 只能调用或解释状态机，不得复制阶段规则。
- BR-002：核心运行时只使用 Python 标准库；MCP 第三方依赖只存在于 MCP 适配层。
- BR-003：G0 与 G1 即使在同一人工闸执行，也必须分别输出检查组、稳定检查 ID 和证据，不得合并后减少检查项。
- BR-004：每个 Spec 必须声明唯一 FEAT；FEAT 在 PRD 索引中只能对应一个当前工作项和一个 Spec，缺失、重复或不一致均阻断。
- BR-005：每条 FR 至少有一条 AC，每条 AC 必须能在设计、任务和验证中找到闭链，不允许孤儿 FR 或孤儿 AC。
- BR-006：代码类变更至少需要一个真实执行的测试命令和成功退出码；纯文档或纯配置变更可走显式人工豁免并留痕。
- BR-007：中风险和高风险 Spec 必须有独立审查证据；低风险 Spec 是否强制审查由 Profile 决定。
- BR-008：安全红线、伪造证据、越权人工动作和状态机绕过不可豁免。
- BR-009：Profile 使用有限声明模型；未知字段、未知阶段、未知检查 ID 和非法人工动作必须显式失败，禁止静默回退。
- BR-010：Spec 创建时冻结 Profile 版本与摘要；后续仓库预设升级不得改变旧 Spec 的 Gate 结果。
- BR-011：`context_bundle` 只读、无副作用、按当前状态生成，默认排除全量 PRD、其他 Spec 和历史聊天。
- BR-012：人工豁免必须记录范围、原因、审批人、创建时间、到期时间和证据；到期后检查自动恢复为未豁免。
- BR-013：Review finding 必须包含 ID、位置、证据、影响、建议、权威依据、严重度、验证状态和是否阻断。
- BR-014：未确认知识只能作为候选；`CONFLICT` 未解决时，相关决策必须阻断或显式标记为待裁决。
- BR-015：未经验证的 Fix Pattern 只能作为参考，不能单独作为阻断依据。
- BR-016：每次状态迁移必须记录 actor、时间、证据和产物哈希；产物变化必须产生新的可追溯记录。

## 4. 功能需求与验收条件

### FR-001 官方标准符合性与核心优势基线

- 功能描述：提供一份可审计的官方标准映射，逐项说明 `sdd-kit` 对 P0–P5、G0–G5 的实现方式、证据位置和剩余缺口，并给出三项核心优势的可量化基线。
- 用户场景：平台维护者、合规人员和业务团队在接入或审计前判断当前能力边界，不依赖口头说明。
- 验收条件：
  - AC-001-1：Given 标准符合性文档已生成，When 审阅任一官方 P0–P5 或 G0–G5 条目，Then 该条目包含实现状态、对应内部动作、证据类型、责任角色和缺口说明，且状态只取“已自动、已人工、部分实现、未实现”之一。【执行路径：本地单元测试 + 人工评审】
  - AC-001-2：Given 三项核心优势需要度量，When 查看基线表，Then “轻量、可自定义、合规可溯源”分别有指标、目标值、采集方式和当前结果，且“轻量”目标为核心零第三方依赖、无服务端、bootstrap 一次。【执行路径：本地单元测试 + 人工评审】
  - AC-001-3：Given 官方 Gate 在任何 Profile 中被执行，When 查看 Gate 报告，Then 每个官方 Gate 均能定位到符合性文档条目，不存在无映射的官方 Gate。【执行路径：本地单元测试】
  - AC-001-4：Given 符合性文档声称某项“已自动”或“已人工”，When 检查对应证据，Then 能定位到实际 CLI 动作、测试或人工记录，不得只写声明。【执行路径：本地测试 + 链接与证据检查】

### FR-002 工作项到 FEAT、Spec、FR/AC 的追溯链

- 功能描述：让 PRD 索引与 Spec 元数据形成机器可读的双向追溯，并在 G0/G1 中分别校验需求侧和规格侧的一致性。
- 用户场景：审计人员从工作项追到 FEAT 和 Spec，或从任一 FR/AC 反向追到工作项和证据。
- 验收条件：
  - AC-002-1：Given 工作项已登记 PRD 索引，When 创建或校验 Spec，Then Spec 元数据中的 FEAT ID 与索引行一致且格式合法，否则阻断。【执行路径：本地单元测试】
  - AC-002-2：Given PRD 索引存在重复 FEAT、同一 FEAT 对应多个当前 Spec 或工作项不一致，When 执行 G0 检查，Then 报告稳定检查 ID、冲突值和修复提示并阻断。【执行路径：本地单元测试】
  - AC-002-3：Given Spec 中存在 FR 没有 AC、AC 前缀找不到对应 FR、AC 重复定义或 AC 无法映射到任务，When 执行 G1/G3 检查，Then 分别报告孤儿 FR、孤儿 AC 和断链 AC 并阻断。【执行路径：本地单元测试】
  - AC-002-4：Given 一个工作项通过 G0 和 G1，When 查看 Gate 报告，Then G0 与 G1 各自包含独立检查组、稳定检查 ID 和通过证据，不允许仅输出一个合并通过结论。【执行路径：本地单元测试】
  - AC-002-5：Given PRD 索引行包含澄清标记，When 执行 G0，Then 非零澄清标记阻断，并准确报告工作项、FEAT 和标记数量。【执行路径：本地单元测试】

### FR-003 最小只读上下文包

- 功能描述：`resume --json` 在当前任务存在时返回稳定 schema 的 `context_bundle`，让 Agent 无需加载全量材料即可完成当前动作。
- 用户场景：Agent 新会话恢复、切换任务、返工或上下文压缩后继续执行。
- 验收条件：
  - AC-003-1：Given 当前 Spec 已进入任务执行阶段，When 调用 `resume --json`，Then `context_bundle` 包含当前 Task、关联 FR/AC、对应设计章节、相关契约、适用项目约束、适用 Fix Pattern、允许改动范围和排除列表。【执行路径：本地单元测试 + 人工评审】
  - AC-003-2：Given 当前 Task 有多个关联 AC，When 生成上下文包，Then 每个 AC 只出现一次，且能定位到设计覆盖行和任务映射行。【执行路径：本地单元测试】
  - AC-003-3：Given 当前没有任务或没有可用上下文，When 调用 `resume --json`，Then 返回完整空结构并保持成功退出，不抛出 KeyError 或写入状态。【执行路径：本地单元测试】
  - AC-003-4：Given 同一状态连续调用两次 `resume --json`，When 比较状态文件、事件文件和 Git 工作区，Then 没有新增、删除或修改，证明上下文生成只读无副作用。【执行路径：本地单元测试 + Git 状态检查】
  - AC-003-5：Given 上下文包中的允许改动范围，When 任务描述或待改文件超出范围，Then Agent 协议要求先停止并请求人工扩大范围，不得静默扩大到整个仓库。【执行路径：本地单元测试 + 人工评审】

### FR-004 G4/G5 可复验证据

- 功能描述：将“写了 PASS”改为“能重放命令并核对退出码、测试定位和审查结论”，阻止文档化伪造通过。
- 用户场景：代码审查、CI 验证、缺陷复盘和发布审计。
- 验收条件：
  - AC-004-1：Given 执行统一验证命令，When 命令结束，Then 证据记录命令文本、执行目录、开始与结束时间、退出码、耗时和关键输出摘要，并绑定当前 Spec、Task 与产物哈希。【执行路径：本地单元测试】
  - AC-004-2：Given 当前变更包含代码文件且 Profile 要求可执行测试，When 没有成功测试命令证据，Then G4/G5 不得自动 PASS，状态不得进入 PR_READY。【执行路径：本地单元测试】
  - AC-004-3：Given 任务表声称某个测试类或测试方法覆盖 AC，When 验证时在测试文件中找不到该测试，Then 报告断链测试并阻断。【执行路径：本地单元测试】
  - AC-004-4：Given 测试文件只在注释或字符串中写 `[AC-xxx]`，When 执行覆盖校验，Then 该标签不算覆盖，必须能定位到真实测试定义和执行记录。【执行路径：本地单元测试】
  - AC-004-5：Given 验证命令退出码非零、超时或未实际执行，When 生成 Gate 5 结论，Then 结论为阻断或未验证，不能写入 PASS。【执行路径：本地单元测试】
  - AC-004-6：Given 变更只涉及文档或配置且没有测试命令，When 人提供带范围的显式豁免，Then G4/G5 可标记为带豁免通过，并在报告、inbox 和指标中保留豁免证据。【执行路径：本地单元测试 + 人工评审】

### FR-005 Workflow Profile v2

- 功能描述：用有限、声明式、可校验的 Profile 定义阶段策略、工件、Gate、检查组合、人工检查点、设计模式、审查要求、风险规则和上下文规则。
- 用户场景：工作流设计者新增团队流程变体，不需要修改核心状态机。
- 验收条件：
  - AC-005-1：Given 一个合法 Profile v2，When 加载并启动新 Spec，Then 声明中的阶段、工件、Gate 策略、检查项、人工检查点、设计模式、审查要求、风险停止规则和上下文规则全部生效。【执行路径：本地单元测试】
  - AC-005-2：Given Profile 含未知字段、未知阶段、未知检查 ID、非法人工动作或缺失必需字段，When 执行 Profile 校验，Then 返回失败并精确定位字段路径和错误原因。【执行路径：本地单元测试】
  - AC-005-3：Given 仅新增 `l2-refactor` Profile，When 启动行为保持型改造 Spec，Then 新流程可运行且核心状态机代码无需为该流程增加分支。【执行路径：本地单元测试 + 人工评审】
  - AC-005-4：Given Spec 创建时冻结了 Profile 版本与摘要，When 仓库后续修改同名 Profile，Then 旧 Spec 继续使用快照，Gate 序列和结果不变。【执行路径：本地单元测试】
  - AC-005-5：Given Profile 将非法 Gate 组合为缺少安全必需检查，When 校验 Profile，Then 拒绝加载并说明不可移除的检查 ID。【执行路径：本地单元测试】

### FR-006 Gate 检查项注册表与分级治理

- 功能描述：为核心检查建立可枚举注册表，统一输出 `pass`、`warn`、`block`，并支持有边界、可到期的人工豁免。
- 用户场景：合规审计、项目自定义策略、例外审批和质量趋势分析。
- 验收条件：
  - AC-006-1：Given 任一 Gate 执行，When 读取检查结果，Then 每项包含检查 ID、所属 Gate、触发方式、级别、是否可豁免、证据要求、责任角色和结果级别。【执行路径：本地单元测试】
  - AC-006-2：Given 建议项失败，When Gate 执行完成，Then 结果为 `warn`，不阻断流转，但必须出现在 Gate 报告和 `inbox` 中并保留原因。【执行路径：本地单元测试】
  - AC-006-3：Given 强制项失败且没有有效豁免，When 尝试 `complete` 或进入下一状态，Then 结果为 `block`，CLI 拒绝迁移并返回检查 ID 与证据要求。【执行路径：本地单元测试】
  - AC-006-4：Given 人创建豁免，When 保存记录，Then 必须包含检查 ID、Spec、Task 范围、原因、审批人、创建时间、到期时间和证据，且 MCP 不暴露该动作。【执行路径：本地单元测试 + 人工评审】
  - AC-006-5：Given 豁免超过到期时间，When 再次执行同一检查，Then 豁免失效并重新按原级别校验，报告中注明“已过期”。【执行路径：本地单元测试】
  - AC-006-6：Given 检查属于安全红线、伪造证据、越权人工动作或状态机绕过，When 请求豁免，Then 系统拒绝并记录拒绝原因。【执行路径：本地单元测试】
  - AC-006-7：Given 多次执行产生 Gate 结果，When 查看指标，Then 可按检查 ID 统计通过率、告警率、阻断率和豁免率。【执行路径：本地单元测试】

### FR-007 按需加载的 Review 契约与技术栈 Overlay

- 功能描述：提供通用审查输出契约，并根据语言、框架和风险加载 Python、Java/Spring、前端 overlay，避免把全部规则塞入 Agent 常驻上下文。
- 用户场景：中高风险代码变更的独立审查，以及低风险变更的轻量自检。
- 验收条件：
  - AC-007-1：Given Spec 风险或 Profile 要求独立审查，When Agent 进入 G4，Then 系统提供通用 Review 契约并只加载与变更技术栈匹配的 overlay。【执行路径：本地单元测试】
  - AC-007-2：Given 审查发现一个问题，When 写入 finding，Then 包含 finding ID、位置、证据、影响、建议、权威依据、严重度、验证状态和是否阻断。【执行路径：本地单元测试】
  - AC-007-3：Given Spec 为 medium 或 high 风险，When 缺少独立审查证据或仍有未关闭阻断 finding，Then G4/G5 阻断；low 风险是否强制由 Profile 决定。【执行路径：本地单元测试】
  - AC-007-4：Given 审查未发现可执行问题，When 生成审查结论，Then 明确写入“未发现可执行问题”及检查范围，不允许空白通过。【执行路径：本地单元测试】
  - AC-007-5：Given 仓库存在 Python、Java/Spring 和前端至少三类 overlay，When 查看入口和加载条件，Then 每类 overlay 有适用范围、权威依据、finding 规则和与通用契约的引用关系。【执行路径：人工评审 + 本地结构检查】
  - AC-007-6：Given Review overlay 运行，When 检查其可执行动作，Then 不包含状态迁移、人工审批或 Gate 规则，只向 Gate 提供结构化事实。【执行路径：本地单元测试】

### FR-008 最小知识基线与冲突处理

- 功能描述：先建立轻量知识索引，记录权威来源、事实、业务规则、冲突和缺口，让 Spec/Design 引用而不是抄写。
- 用户场景：跨服务需求澄清、业务规则确认、知识过期排查和审计取证。
- 验收条件：
  - AC-008-1：Given 知识索引已建立，When 审阅索引，Then 记录只能分类为 `SRC`、`FACT`、`BR`、`CONFLICT` 或 `GAP`，每类有明确含义和稳定 ID。【执行路径：本地单元测试 + 人工评审】
  - AC-008-2：Given 新增一条知识记录，When 校验记录，Then 包含权威位置、版本或 Commit、适用范围、Owner、确认状态和关联 FEAT/FR/AC。【执行路径：本地单元测试】
  - AC-008-3：Given 知识记录没有权威来源，When 写入索引，Then 只能标记为候选，不能标记为 `CONFIRMED`。【执行路径：本地单元测试】
  - AC-008-4：Given 存在未解决 `CONFLICT`，When 相关 Spec 或 Design 引用该知识，Then 决策被阻断或显式标记为待裁决，并在 Gate 报告中可见。【执行路径：本地单元测试】
  - AC-008-5：Given 至少一个真实 Spec 使用知识索引，When 检查 Spec 与 Design，Then 业务规则通过稳定知识 ID 引用，未复制权威正文。【执行路径：人工评审 + 本地链接检查】

### FR-009 BAR、Fix Pattern 与可执行检查闭环

- 功能描述：把真实缺陷复盘转换为可复用 Pattern、可执行检查和回归测试，并让后续任务按需看到适用补丁。
- 用户场景：缺陷复盘、同类问题预防、上下文增强和质量趋势回流。
- 验收条件：
  - AC-009-1：Given 一个真实缺陷完成 BAR，When 生成 Fix Pattern，Then 记录症状、根因、触发条件、修复、预防检查、适用范围、Owner 和状态，并关联至少一个可执行 `CHK`。【执行路径：本地单元测试 + 人工评审】
  - AC-009-2：Given 当前 Task 与已验证 Fix Pattern 的适用范围匹配，When 生成 `context_bundle`，Then 自动带入 Pattern ID、摘要和检查命令；不匹配时不加载。【执行路径：本地单元测试】
  - AC-009-3：Given 至少一个真实缺陷走完 `BAR → FP → CHK → 回归测试`，When 回放证据，Then 能定位缺陷来源、Pattern、检查、回归测试和通过退出码。【执行路径：本地单元测试 + 人工评审】
  - AC-009-4：Given Fix Pattern 尚未验证，When 被当前任务引用，Then 只标记为参考信息，不得单独作为阻断依据。【执行路径：本地单元测试】
  - AC-009-5：Given 多次任务产生质量数据，When 查看指标，Then 增加豁免率、逃逸缺陷、重开率和 Gate 一次通过率，并说明口径与采集来源。【执行路径：本地单元测试 + 人工评审】

### FR-010 兼容性、审计回放与发布一致性

- 功能描述：保证新增能力不破坏旧 Spec、旧 CLI 调用和轻量部署方式，并同步版本、文档、manifest 与测试。
- 用户场景：平台升级、已接入仓库继续使用、审计回放和发布验收。
- 验收条件：
  - AC-010-1：Given 一个升级前创建的旧 Spec 已有 Profile 快照，When 使用新版本 CLI 执行 `resume`、`check` 和状态迁移，Then 继续按旧快照解释，不因新预设或新检查 ID 漂移。【执行路径：本地单元测试】
  - AC-010-2：Given 任一人工或自动状态迁移，When 审计事件链，Then 能看到 actor、时间、迁移前后状态、证据、产物哈希和下一步，且不能通过手改事件文件伪造。【执行路径：本地单元测试 + 人工评审】
  - AC-010-3：Given 现有脚本只依赖既有 `next.action`、`submit_with` 和基础 JSON 字段，When 升级到本 Spec 实现，Then 原有字段保持兼容，新增字段只做向后兼容扩展。【执行路径：本地单元测试】
  - AC-010-4：Given 核心、提示词或模板发生变化，When 执行发布检查，Then 版本号、manifest、README、执行手册和 Agent 协议均已同步且一致性校验通过。【执行路径：本地单元测试 + 发布检查】
  - AC-010-5：Given 本 Spec 全部任务完成，When 执行全量单元测试、核心校验、Agent 校验和 CI 检查，Then 全部命令成功且没有跳过关键 AC。【执行路径：全量测试 + CI】
  - AC-010-6：Given 新功能已交付，When 统计正常 `l2-standard` 流程，Then 每阶段对 Agent 仍只暴露一个动作和一个提交命令，计划内人工检查点数量不增加。【执行路径：本地快照测试 + 人工评审】

## 8. 数据模型

- 核心实体定义：FEAT 追溯记录、Profile 快照、检查项定义、检查结果、验证证据、人工豁免、Review finding、知识记录、Fix Pattern 和指标快照。
- 数据流说明：PRD 索引与 Spec 提供需求链；Profile 快照决定当前阶段策略；Gate 执行读取工件与证据并生成结构化结果；人工动作写入审计事件；指标从事件和检查结果聚合，不从手工文本推断。
- 持久化边界：不新增数据库；原有状态、事件、快照和报告文件继续作为仓库内可审计持久层。
- 版本与兼容：新增 schema 必须声明版本；读取方对未知字段保持宽容，对缺失必需字段明确失败。

## 9. 约束与假设

- 技术约束：核心只使用 Python 标准库；MCP 依赖隔离；所有命令可在仓库根目录直接执行。
- 技术约束：`sdd/scripts/sdd.py` 是唯一状态机；`sdd/core.py` 继续通过子进程调用状态机。
- 技术约束：MCP 只是薄适配器，不包含独立 Gate、状态规则或人工动作。
- 业务约束：`approve`、`merge`、`unblock`、`rewind` 和 Gate 豁免只能由人执行。
- 业务约束：`l2-standard` 的计划内人工检查点保持为 Spec 确认和 PR 合并两个。
- 业务约束：官方 Gate 的“已自动、已人工、部分实现、未实现”必须如实标注，不得为了提高覆盖率虚构状态。
- 假设条件：代码类变更默认至少需要一个成功测试命令；纯文档和纯配置变更可通过显式人工豁免通过。
- 假设条件：中风险和高风险 Spec 默认要求独立 review；低风险是否强制由 Profile 配置。
- 假设条件：首个自定义 Profile 采用 `l2-refactor`，用于行为保持型存量改造。
- 假设条件：旧 Spec 的 Profile 快照和事件历史保留在仓库内，不要求集中式迁移。

## 11. AI能力规格

不适用。`sdd-kit` 是确定性 SDD 执行内核，不提供模型推理能力；Agent 能力由外部执行器提供，本 Spec 只约束其输入上下文、输出证据和人工边界。

## 12. 上下文与知识规格

- 上下文单位：当前 Spec、当前 Task、关联 FR/AC、设计覆盖行、相关契约、项目约束、允许改动范围、排除列表和适用 Fix Pattern。
- 上下文选择：由当前状态和任务映射确定，默认不加载全量 PRD、其他 Spec 或历史聊天。
- 知识引用：Spec/Design 通过稳定知识 ID 引用 `FACT/BR`，不得复制权威正文；`CONFLICT/GAP` 必须显式暴露。
- 知识权威顺序：明确 Owner 的业务规则优先于代码现状；代码现状只能证明实现事实，不能自动成为已确认业务规则。

## 13. 统计性验收标准

不涉及。本 Spec 的验收均可由确定性测试、CLI 退出码、结构化报告、Git 状态和人工证据检查判定。

## 14. AI安全合规

- 人工动作隔离：`approve`、`merge`、`unblock`、`rewind` 和豁免必须要求人类显式标志，MCP 不暴露。
- 提示与上下文安全：`context_bundle` 只提供完成任务所需最小内容，降低越权读取和无关信息污染。
- 证据完整性：Gate 结果绑定检查 ID、命令、退出码和产物哈希，防止以自然语言声明替代可复验事实。
- 安全红线：安全类强制检查不可豁免；伪造测试、伪造审查和篡改状态事件必须阻断并留痕。

## 15. 成本与性能

- 不新增托管服务和数据库成本。
- 不新增核心运行时第三方包安装成本。
- `resume --json` 默认只读取当前 Spec 的映射与 Profile，不进行全仓库内容检索。
- 指标聚合离线进行，失败时可从事件和报告重建，不阻塞正常状态迁移。

## 16. 运行监控与效果度量

| 指标 | 口径 | 目标 |
|---|---|---|
| 核心第三方依赖数 | 核心运行路径实际导入的非标准库包数量 | 0 |
| 服务端组件数 | 新增长期运行服务或数据库数量 | 0 |
| 正常阶段命令数 | Agent 每阶段需要理解的动作数 | 1 个动作 + 1 个提交命令 |
| 计划内人工检查点数 | `l2-standard` 的固定人工闸 | 2 |
| Profile 校验覆盖率 | 所有 Profile 字段和引用均被 schema 校验 | 100% |
| FEAT 追溯完整率 | 有唯一 FEAT 且 FEAT→Spec→FR/AC→Task→证据完整的 Spec 占比 | 100% |
| Gate 一次通过率 | 首次执行即无 block 的 Gate 数 / Gate 总数 | 趋势监控 |
| 豁免率 | 带有效豁免通过的强制检查数 / 强制检查总数 | 趋势监控并设置阈值告警 |

## 17. 自主程度与人机分工

不适用“仅 AI 原生·L4 产品填写”的自主等级，但本 Spec 明确人机边界：

- 人负责工作项确认、Spec 确认、方案裁决、例外审批、PR 合并和最终业务责任。
- Agent 负责调研、生成工件、实现任务、执行命令、提交证据和在阻断时停止。
- 状态机负责判定下一动作和是否允许迁移，Agent 不得自行解释或跳过。

## 18. Agent行为规格

- Agent 每次恢复先读取 `next.action` 和 `context_bundle`，不询问开发者当前阶段。
- Agent 只执行当前动作；`ok=false` 时按结构化错误修复后重试。
- Agent 遇到 `decision_required`、人工检查点、超出允许改动范围、未解决冲突或不可豁免阻断时停止并交给人。
- Agent 不手改状态文件、事件文件、Profile 快照或人工证据。
- Agent 不把注释中的 AC 标签、未执行的测试名或空白 Review 结论当作通过证据。

## 19. 审计与回放

- 回放单位：一次状态迁移、一次 Gate 执行或一次人工动作。
- 必需字段：actor、时间、Spec、Task、检查 ID、状态迁移前后值、证据、产物哈希和下一步。
- 回放入口：从工作项追到 FEAT、Spec、FR/AC、Task、验证命令、Gate 结果和 PR；也应支持反向追溯。
- 篡改防护：事件记录与产物哈希不一致时，审计报告必须标记异常并阻断发布。
- 保留策略：随 Git 历史保留；不新增集中式归档服务。

## 20. 多智能体协同

不要求多智能体架构。若使用多个 Agent，由主 Agent 保持写权限协调，任务必须按 `context_bundle` 的允许范围和文件所有权拆分；子 Agent 不得自行审批、合并、解除阻塞或创建平行状态机。

- [x] Spec ID 格式正确，并与目录名一致。
- [x] 工作项 ID 存在且不含前导 `%`。
- [x] FEAT ID 与 PRD 索引一致。
- [x] In-Scope 和 Out-of-Scope 均已明确填写。
- [x] FR/AC 编号唯一、稳定，每个 FR 至少包含一条 AC。
- [x] 每条 AC 包含可判定的 Given/When/Then，并可映射到本地测试或人工证据。
- [x] 边界、异常、非功能需求、接口、数据模型和约束均已填写或明确不涉及。
- [x] 残留澄清标记为 0。
- [x] 变更历史已更新，未创建平行版本文件。
