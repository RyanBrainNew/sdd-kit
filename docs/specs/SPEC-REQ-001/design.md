## 2. 设计目标

- 核心问题：Gate 产物哈希直接读取工作区字节，导致同一文本在 CRLF 和 LF 检出方式下得到不同 SHA-256；历史 `state.json` 又记录了 CRLF 哈希，最终让干净的 LF 工作区无法通过 `check`。
- 设计范围：文本工件的规范化哈希、历史哈希兼容、Gate 记录和审批记录的统一哈希入口、测试，以及 GitHub Actions 的 SDD 门禁步骤。
- 非设计范围：不改变状态机阶段、不修改人工动作、不对二进制工件规范化、不实现 issue #8 的 reapprove/change-set/trace。

## 3. 方案概述

- 高层方案：在 `sdd/scripts/sdd.py` 内增加统一的文本工件哈希入口。文本工件先解码为 UTF-8，再把 `CRLF` 和孤立 `CR` 统一转换为 `LF`，最后计算 SHA-256；非 UTF-8 或非文本扩展名退回原始字节哈希。
- 关键决策：
  1. 新记录使用 LF 规范化哈希，和仓库 `.gitattributes` 的 `eol=lf` 约定一致。
  2. 校验时从当前文件生成原始、LF、CRLF 三种候选哈希，与历史记录比较；这样历史 CRLF 哈希和未来 LF 哈希都能验证。
  3. 只放宽“行尾表示差异”，不放宽正文变化；正文变化时三种候选都不等于历史哈希。
  4. `tasks.md#plan` 继续使用已有的结构化 `task_plan_hash()`，不纳入本次文本哈希改造。
- 方案对比：
  - 只改 `.gitattributes` 为 CRLF：会改变全仓库文本约定，且不能兼容已有 LF 记录，放弃。
  - 手工迁移所有历史 `state.json`：违反“不手改审计文件”约束，放弃。
  - 统一规范化哈希并兼容历史候选：改动集中、可回归、兼容旧记录，采用。

## 5. 系统架构

### 5.1 架构图

```text
工件文件
  -> artifact_sha256()
     -> 文本扩展名且 UTF-8 可解码
        -> CRLF/CR 规范化为 LF
        -> SHA-256
     -> 其他情况
        -> 原始字节 SHA-256
  -> artifact_digest() / Gate 报告 / state.artifact_hashes
  -> check_gates()
     -> 当前文件生成原始/LF/CRLF 候选
     -> 与历史记录比较
```

### 5.2 模块划分

| 模块/服务 | 职责 | 输入 | 输出 | 依赖 |
|---|---|---|---|---|
| `sdd/scripts/sdd.py` | 唯一状态机；规范化工件哈希和兼容校验 | 工件路径、历史哈希 | Gate 结果、报告、状态哈希 | Python 标准库 |
| `tests/test_sdd.py` | 回归测试哈希、Gate 和兼容性 | 临时仓库与工件 | 测试结果 | `unittest` |
| `.github/workflows/tests.yml` | 在 CI 中执行单元测试和 SDD 门禁 | Git 提交 | CI 通过/失败 | GitHub Actions |
| `README.md` / `sdd/README.md` | 说明跨平台哈希和 CI 行为 | 无 | 使用说明 | 无 |

### 5.3 模块间交互

1. `submit`、`approve`、`complete` 和 `merge` 通过 `artifact_digest()` 或统一哈希函数记录工件摘要。
2. `check_gates()` 读取报告中的历史摘要，用当前文件生成候选摘要后比较。
3. CI 在单元测试之后串行执行三项 SDD 门禁；任一步返回非 0 即终止 job。

## 6. 数据模型

- 实体定义：`artifact_hashes` 仍以“相对路径 -> SHA-256 字符串”保存，不新增必填字段。
- 数据库变更：不涉及。
- 事务边界：不涉及。
- 迁移方案：不迁移历史记录；通过候选哈希兼容 CRLF 历史值。新记录使用 LF 哈希。

## 7. 接口契约

| 方法 | 路径 | 描述 | 归属AC |
|---|---|---|---|
| CLI | `python -m sdd submit` | 校验并记录工件 | AC-001-2；AC-002-3 |
| CLI | `python -m sdd check` | 校验历史哈希和当前文件 | AC-001-3；AC-002-1 |
| CI | GitHub Actions | 执行 SDD 三项门禁 | AC-003-1；AC-003-2 |

- 请求/响应结构：CLI 输出保持现有 JSON/文本格式，不新增字段。
- 错误码：沿用现有非 0 退出码和 `errors` 数组。
- 兼容性：历史 CRLF 哈希继续可用；新哈希为 LF；二进制哈希不变。
- 契约文件：不涉及。

## 8. 认证、授权、幂等与安全

- 认证：不涉及。
- 授权：不新增人工动作；`approve`、`merge`、`unblock`、`rewind` 仍为 human-only。
- 幂等：同一文本内容重复计算哈希结果稳定。
- 敏感数据：只读取仓库内工件，不新增网络传输。
- 审计：Gate 报告和 `state.json` 继续保存可复验的 SHA-256，正文变化仍会改变哈希。

## 9. 关键决策ADR

- 引用：无需新增 ADR，决策记录在本设计第 3 节。
- 判断依据：改动局限在哈希入口和校验比较，不改变状态机、数据模型或部署边界。

## 10. 非功能需求设计

- 性能设计：每个工件只读取一次；候选哈希只做内存中的小规模字节扫描，不引入额外进程。
- 可用性设计：历史记录无需迁移；LF 和 CRLF 工作区都可继续使用。
- 可观测性：现有 Gate 报告保留哈希、检查项和错误信息，不新增外部监控依赖。

## 11. 依赖与风险

| 风险/依赖 | 影响 | 缓解措施 | 负责人 |
|---|---|---|---|
| 兼容逻辑过宽 | 可能把真实正文修改误判为行尾变化 | 增加正文变化回归测试，确保三个候选都不匹配 | sdd-kit 平台维护者 |
| 历史记录格式不一致 | 解析失败或漏报 | 只解析现有 Gate 报告结构，不新增格式 | sdd-kit 平台维护者 |
| 非 UTF-8 工件 | 解码失败 | 捕获解码错误，退回原始字节哈希 | sdd-kit 平台维护者 |
| CI 门禁步骤导致 PR 首次失败 | 阻塞交付 | 在本地先跑三项门禁，并使用带 `Spec-Id` / `Task-Id` 的提交信息 | sdd-kit 平台维护者 |

## 12. 回滚方案

- 触发条件：规范化哈希导致历史 Spec 误阻断，或 CI 门禁无法在干净工作区通过。
- 回滚步骤：回退本次提交，重新生成 `sdd/manifest.json`，恢复旧版 CI 步骤。
- 数据恢复：不涉及数据库；历史 `state.json` 未被改写，无需数据迁移。
