## 2. 范围声明

- In-Scope：修复 SDD 文本工件哈希对 CRLF/LF 敏感的问题，并让 CI 执行文档声明的 SDD 门禁。
  1. 对 Markdown、JSON、YAML 和纯文本等 SDD 文本工件，按 LF 规范化内容计算稳定哈希。
  2. 同一文本内容分别以 CRLF 和 LF 保存时，计算出的工件哈希必须一致。
  3. `check` 必须兼容历史 `state.json` / Gate 报告中已经记录的 CRLF 哈希，不能要求手工改写审计文件。
  4. 仅行尾变化不得触发“工件已被修改”；正文语义变化仍必须阻断。
  5. GitHub Actions 必须实际执行 `verify-core`、`verify-agent` 和 `check --all --stage ci --check-git`。
  6. 同步测试、README、`sdd/agent-contract.md`、版本号和 manifest。
- Out-of-Scope：不改变 SDD 状态机、Gate 语义、人工检查点或部署形态。
  1. 不新增或修改 `approve`、`merge`、`unblock`、`rewind` 的人工属性。
  2. 不为已合并历史 Spec 重新执行 Gate、rewind 或人工再审批。
  3. 不对 PNG、PDF、ZIP 等二进制工件做文本行尾规范化；二进制仍按原始字节哈希。
  4. 不改变 `sdd/manifest.json` 的受保护文件完整性语义。
  5. 不引入服务端、数据库、常驻进程或新的第三方运行时依赖。
  6. 不实现 issue #8 的 reapprove、change-set、trace 或全量 commit 审计。

## 3. 业务上下文

### 3.1 干系人与角色

| 角色 | 诉求 | 使用场景 | 责任边界 |
|---|---|---|---|
| 平台维护者 | 同一提交在不同工作区和操作系统上得到相同的 Gate 结论 | 发布校验、跨平台排查、CI 维护 | 维护核心哈希规则与 CI |
| 业务仓库开发者 | 不需要手工修 `state.json` 就能在 Windows 和 Linux 上工作 | 本地提交、切换工作区、执行检查 | 只维护业务 Spec 和代码 |
| 执行 Agent | 按 CLI 返回结果修复问题，不因行尾差异误判 | 提交工件、读取 Gate 错误、重试 | 不手改状态机审计文件 |
| 审计与合规 | 历史哈希仍可验证，语义变化仍能阻断 | 审计 Gate 报告、复核证据 | 只读审计，不代替人工确认 |

### 3.2 业务流程

1. Agent 写入 Spec、Design、Tasks 或验证工件。
2. CLI 对文本工件计算规范化后的稳定哈希，并写入 Gate 报告和状态记录。
3. 同一内容在 CRLF 或 LF 工作区被重新检出时，`check` 仍判定为同一工件。
4. 正文发生语义变化时，即使字节长度相同，`check` 仍判定为被修改并阻断。
5. CI 在单元测试之后执行 SDD 三项门禁，任一失败即阻止合并。

### 3.3 业务规则

- BR-001：唯一状态机仍是 `sdd/scripts/sdd.py`；哈希兼容规则不得复制到 MCP 或文档中。
- BR-002：`approve`、`merge`、`unblock`、`rewind` 继续只能由人执行。
- BR-003：CRLF 与 LF 只是同一文本的表示差异，不得被视为业务内容变化。
- BR-004：历史 CRLF 哈希必须继续可验证；兼容逻辑不得放过真实的正文修改。
- BR-005：仓库 `.gitattributes` 的 LF 约定是规范化基准；新产生的工件哈希统一使用 LF。
- BR-006：GitHub Actions 必须执行 `AGENTS.md` 声明的 SDD 门禁，不能只跑单元测试。

## 4. 功能需求与验收条件

### FR-001 文本工件稳定哈希

- 功能描述：对 SDD 文本工件按 LF 规范化内容计算哈希，使相同内容不受 Windows CRLF 与 Unix LF 检出方式影响。
- 用户场景：开发者在 Windows 写入工件、在 Linux CI 重新检出后，Gate 仍认为工件未变化。
- 验收条件：
  - AC-001-1：Given 同一段 UTF-8 文本分别保存为 CRLF 和 LF，When 计算工件哈希，Then 两次 SHA-256 完全相同。【执行路径：本地单元测试】
  - AC-001-2：Given Gate 绑定的文本工件只发生 CRLF/LF 行尾变化，When 执行 `check`，Then 不输出“工件已被修改”。【执行路径：本地单元测试】
  - AC-001-3：Given 文本正文发生语义变化，When 执行 `check`，Then 仍输出“工件已被修改”并阻断流转。【执行路径：本地单元测试】

### FR-002 历史 CRLF 哈希兼容

- 功能描述：校验时识别历史状态中记录的 CRLF 哈希，使旧 Spec 不需要手工修改 `state.json` 即可在 LF 工作区通过。
- 用户场景：平台升级后，开发者重新 clone 仓库，历史已合并 Spec 不会因为行尾转换而失败。
- 验收条件：
  - AC-002-1：Given `state.json` 中是历史 CRLF 哈希，When 在 LF 工作区执行 `check`，Then 同一内容通过校验。【执行路径：本地单元测试】
  - AC-002-2：Given `state.json` 中是历史 CRLF 哈希，When 工件正文被修改，Then 校验仍然失败。【执行路径：本地单元测试】
  - AC-002-3：Given 工件以 CRLF 写入并产生新的 Gate 记录，When 查看报告或状态中的哈希，Then 记录的是规范化 LF 哈希。【执行路径：本地单元测试】

### FR-003 CI 门禁与文档对齐

- 功能描述：GitHub Actions 在推送和 PR 上执行 SDD 三项门禁，并保持现有 Python 3.11/3.12 测试矩阵。
- 用户场景：维护者通过 CI 直接看到核心完整性、Agent 契约和全部 Spec 工件校验结果。
- 验收条件：
  - AC-003-1：Given GitHub Actions 工作流文件，When 解析其步骤，Then 同时包含 `python -m sdd verify-core`、`python -m sdd verify-agent` 和 `python -m sdd check --all --stage ci --check-git`。【执行路径：本地单元测试】
  - AC-003-2：Given SDD 门禁步骤，When 任一命令返回非 0，Then 工作流失败且不设置 `continue-on-error`。【执行路径：本地单元测试】
  - AC-003-3：Given 干净的 LF 工作区，When 执行三项 SDD 门禁，Then 三项全部通过。【执行路径：本地单元测试 + CI 集成测试】

## 5. 边界与异常

| 场景类型 | 场景描述 | 关联FR/AC | 预期行为（错误码/降级策略/提示信息） |
|---|---|---|---|
| 边界场景 | 同一文本文件混用 CRLF 和 LF | FR-001；AC-001-1 | 统一规范化为 LF 后计算哈希 |
| 边界场景 | 历史状态只有 CRLF 哈希，没有原文 | FR-002；AC-002-1 | 同时尝试原始、LF 和 CRLF 候选哈希，命中即通过 |
| 异常场景 | 正文修改但文件字节数与原文相同 | FR-001；AC-001-3 | 哈希不同，输出“工件已被修改”并阻断 |
| 异常场景 | 非 UTF-8 二进制工件 | FR-002；AC-002-2 | 不猜测编码，继续按原始字节哈希 |

## 6. 非功能需求

| 类型 | 要求 | 指标/验收方式 | 关联FR/AC |
|---|---|---|---|
| 性能 | 哈希计算只读取一次工件内容，不引入网络或额外进程 | 现有测试和代码评审 | FR-001 |
| 安全 | 兼容逻辑不得放过真实内容修改 | 语义变化回归测试 | FR-001；AC-001-3 |
| 可用性 | 旧 Spec 不需要迁移命令或手工修状态文件 | 历史哈希回归测试 | FR-002；AC-002-1 |

## 8. 数据模型

- 核心实体定义：Gate 报告和 `state.json` 中的 `artifact_hashes` 仍保存 SHA-256 字符串，不新增必填字段。
- 数据流说明：文本工件读取后规范化为 LF，再计算哈希；校验时对当前文件生成原始和规范化候选哈希，与历史记录比较。

## 9. 约束与假设

- 技术约束：只使用 Python 标准库；核心哈希逻辑位于唯一状态机 `sdd/scripts/sdd.py`。
- 业务约束：不改变既有状态、Gate 和人工动作语义；历史审计记录保持可读。
- 假设条件：SDD 文本工件使用 UTF-8；非 UTF-8 文件按二进制处理。
